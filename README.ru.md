# D103CN FEL root

**Первый успешный root: прошивка `4.5.6_1409`, плата `R2405 v4`, Athena Linux `r2405_release`.**

UART-root через физическое подключение для Xiaomi Mijia M30S (`xiaomi.vacuum.d103cn`). [English](README.md) · [Исследование / SSH](https://github.com/Dark-V/D103CN_root/wiki)

**Экспериментальный переносимый v2.** Персонализированный v1 дал UART- и SSH-root на одном R2405 v4 с прошивкой 4.5.6_1409. Новый worker/writer с поиском файла собран; офлайн-разбор проверен на двух сохранённых снимках **того же аппарата**. **v2 на плате ещё не запускался. Это не проверенный однокнопочный установщик.**

Новые продолжение чтения с выборочной сверкой и режим подтверждения неполного бэкапа на аппарате также ещё не проверялись.

## Принцип

FEL загружает временный код в SRAM/RAM. Собственный бэкап даёт заводские компоненты DDR/NAND. Через заводской NFTL и разбор ext4 находится `/data/config/miio/device.conf`; в него добавляется короткая команда UART-shell. При обычной загрузке штатный root-процесс выполняет конфиг как shell-код.

Сектор и содержимое файла вычисляются для подключённого аппарата. Заводские настройки сохраняются. Чужие страницы, готовые приватные файлы автора, HAR, cookies, аккаунты, общие SSH-ключи и загрузка прошивки из Интернета не нужны. Компилятор ARM и ELF-файлы пользователю не требуются.

Подписанные boot/rootfs не заменяются; RSA не взламывается. Нет запуска стороннего Linux, отключения термозащиты, NAND ERASE или автоматической установки SSH. Но APPLY **записывает NAND**: одну логическую страницу 4 КиБ через заводской NFTL и парный PROGRAM. Физической атомарности нет. Ошибка, неподдерживаемая разметка или потеря питания могут окирпичить устройство. Полное восстановление из raw-бэкапа **не проверено**. OTA `.bin` не является raw-образом для восстановления NAND.

Принимаются только закреплённые хешами D103CN-загрузчик/DDR, SoC `1755`, NAND `98 da 90 15 76 16 08 00`, RAM 512 МиБ, 462848 логических секторов и изученные форматы ext4/JBD2. Неизвестные заводские профили/разметки, существующие hooks и конфиги без места для замены прежнего размера отклоняются. Не обходите проверки. Версию активной Linux-прошивки инструмент отдельно не определяет: совпавший загрузчик не доказывает совпадение скриптов rootfs. Hook зависит от штатной ветки запуска Wi-Fi/BLE; сама запись файла ещё не доказывает её срабатывание. Сброс Wi-Fi/OTA могут удалить доступ.

## 1. Подготовка

Python 3.10+ (разработка на 3.12). В Windows нужен совместимый libusb-драйвер **именно** для `VID_1F3A:PID_EFE8`; не меняйте драйверы других устройств. Универсального проверенного pinout здесь нет: не замыкайте случайные площадки. Используйте стабильное питание, изолируйте открытую электронику; при реальном перегреве или проблемах питания остановитесь. [FEL и предосторожности](https://github.com/Dark-V/D103CN_root/wiki/FEL-method-ru), [ограничения восстановления](https://github.com/Dark-V/D103CN_root/wiki/Backup-and-recovery-ru).

В PowerShell, из каталога репозитория:

```powershell
py -3 -m venv .venv
.venv\Scripts\python.exe -m pip install -r requirements.txt
.venv\Scripts\python.exe exploit.py
```

Без аппаратных флагов USB не открывается. Используйте только для собственного устройства либо с разрешения владельца. Введите плату в свежий FEL по проверенной для вашей ревизии процедуре и подключите USB. UART — отдельное подключение.

## 2. Полный приватный бэкап

Команда явно запускает закреплённый read-only SRAM-ридер и читает BootROM плюс всю NAND с OOB. Есть прогресс, журнал хешей и проверка сохранённого файла:

```powershell
.venv\Scripts\python.exe exploit.py --capture --out ..\D103CN-private\backup-01
```

Полный бэкап — 285212672 байта. На этой плате FEL может отключаться/уходить в сон примерно через 20–30 минут. При отключении чтение прекращается; проверенный префикс и receipt сохраняются. Верните плату в **свежий FEL** и явно продолжите в **том же каталоге**:

```powershell
.venv\Scripts\python.exe exploit.py --resume-capture ..\D103CN-private\backup-01
```

Resume проверяет хеш каждого сохранённого блока, заново читает до 256 ранее сохранённых физических страниц в 32 пачках и дописывает с последней проверенной страницы только при совпадении. Начало заново не читается целиком и не перезаписывается. Расхождение, повреждённый журнал или хвост без записи в журнале останавливают инструмент, а не разрешают удаление данных. После следующего сна команду можно повторить. Между сеансами не загружайте штатную ОС. Выборка не доказывает неизменность всей NAND; многосеансовый бэкап не является атомарным снимком. Автоповтора нет; прерванный APPLY так продолжать **нельзя**.

Неполный бэкап тоже можно использовать осознанно, через отдельное подтверждение ниже. Для извлечения заводских компонентов достаточно первых **4096 проверенных физических страниц** (8912896 байт); это минимум для входных файлов, не полный набор данных для восстановления. Каталог `D103CN-private` **никогда не публикуйте**: там данные и секреты устройства.

Затем офлайн извлеките компоненты **из своего бэкапа**:

```powershell
.venv\Scripts\python.exe exploit.py --extract-factory ..\D103CN-private\backup-01\nand.raw.bin --brom ..\D103CN-private\backup-01\brom.bin --out ..\D103CN-private\factory-01
```

TOC0 исправляется BCH80 и сверяется по SHA256; копии TOC1 проверяются BCH32, нужные компоненты — отдельными хешами. DDR-trainer собирается локально из извлечённого TOC0; ничего из Интернета не скачивается.

## 3. Поиск файла и PREPARE — без разрешения PROGRAM

Полностью перезапустите питание и снова войдите в FEL. Начало проверенного захвата должно быть моложе шести часов. По умолчанию требуется полный бэкап. Перед подготовкой инструмент заново читает 256 уже сохранённых физических страниц в 32 пачках, включая случайные, и сравнивает их с бэкапом. Выборка не доказывает совпадение всей памяти.

```powershell
.venv\Scripts\python.exe exploit.py --prepare --inputs ..\D103CN-private\factory-01 --backup ..\D103CN-private\backup-01\receipt.json --session ..\D103CN-private\session-01 --accept-unverified-hardware
```

Проверяются MBR, ext4, allocation bitmap, inode, mapping и журнал. Значения конфигурации и соседние байты сохраняются. Метаданные, использованные при поиске, перечитываются. Во время поиска PROGRAM и ERASE запрещены. `PREPARE_OK` означает готовый проверенный кандидат, **не установленный root**. При отказе остановитесь; не подставляйте чужие файлы или адреса.

Если осознанно идёте дальше с неполным проверенным префиксом, добавьте `--accept-partial-backup` **и к PREPARE, и к APPLY**. Это не делает бэкап полным и не обещает восстановление. Заводские профили, live-страницы и остальные проверки по-прежнему обязательны.

## 4. Отдельная однократная запись

После PREPARE **не отключайте и не перезапускайте плату**. В течение десяти минут, в той же RAM-сессии:

```powershell
.venv\Scripts\python.exe exploit.py --apply --session ..\D103CN-private\session-01 --accept-unverified-hardware --accept-nand-write
```

Перед попыткой записи APPLY показывает целевой сектор и число сохранённых страниц, затем просит ввести `WRITE <сектор>` в интерактивной консоли. При `--accept-partial-backup` фраза другая: `WRITE <сектор> WITHOUT FULL BACKUP`. Иной ответ или EOF отменяет операцию до открытия USB и расходования попытки записи. Одного флага, pipe или ответа по умолчанию недостаточно. Неполный бэкап не выдаётся за полный.

Снова проверяются live-страницы; разрешается одна попытка парного PROGRAM, затем flush и native readback. `NATIVE_READBACK_OK` ещё не доказывает root в штатной ОС или независимое физическое восстановление. Маркер `APPLY-CONSUMED` запрещает повтор той же попытки. При тайм-ауте/ошибке сохраните всё для разбора: **не удаляйте маркер и не повторяйте вслепую**. Команд ERASE, автоматической перезагрузки и автоматического raw-restore нет.

После успеха загрузите аппарат **обычно, без FEL**. UART: подходящий адаптер, проверенные уровни/распиновка, 115200 8N1, flow control выключен. Не подавайте 5 В на сигнальные контакты. Нажмите Enter:

```sh
id
```

Нужен `uid=0(root)` именно в штатной ОС. Добавленный hook:

```sh
sh<>/dev/ttyS0>&0&
```

Это физический root-shell без пароля, не заводской login prompt. Не публикуйте `device.conf`.

## 5. Исправление нескольких UART-shell

При повторном чтении конфига запускаются несколько shells: `id` превращается в `i`/`di`, символы теряются, вывод перемешивается с логами. Root от этого не исчезает. На первом аппарате помогла замена короткого hook на:

```sh
mkdir /tmp/d103-uart 2>/dev/null && setsid /sbin/getty -n -l /bin/sh -L 115200 ttyS0 &
```

`uart-fix.sh` делает эту замену из **штатного root-shell**, сохраняя резервную копию конфига и заводские значения. Передайте файл локально через UART или уже работающий AP пылесоса. Пример: ПК подключён к AP, адрес ПК — `192.168.5.100`, пылесоса — `192.168.5.1`. Раздайте только публичную папку:

```powershell
py -3 -m http.server 8765 --bind 192.168.5.100 --directory .
```

В UART по одной команде, без текста приглашения:

```sh
curl -f http://192.168.5.100:8765/uart-fix.sh -o /tmp/uart-fix.sh
sha256sum /tmp/uart-fix.sh
```

Сравните с `Get-FileHash .\uart-fix.sh -Algorithm SHA256` на ПК, затем:

```sh
sh /tmp/uart-fix.sh
```

Остановите HTTP-сервер и выполните **обычную перезагрузку**, чтобы убрать старые процессы. Снова проверьте `id`. `/tmp`-блокировка исчезает при перезагрузке; завершившийся getty в текущей сессии автоматически не перезапускается.

## 6. SSH после рабочего UART-root

[Установка SSH и подключение Wi-Fi](https://github.com/Dark-V/D103CN_root/wiki/SSH-ru). Необязательный пакет, его исходники и лицензии вынесены в Wiki. Для входа создаётся собственный Ed25519-ключ, на пылесосе генерируется уникальный host key. systemd, общий пароль root и общий ключ авторизации не нужны. Готовый SSH-addon поддерживает только указанные в инструкции AP/LAN-подсети и не является WAN-firewall. После обычной перезагрузки обязательно проверьте вход ещё раз.

В основном дереве — только runtime рута, UART-фикс и инструкции. Исследование, native-исходники, сборка и результаты проверок находятся в [Wiki](https://github.com/Dark-V/D103CN_root/wiki). Собственный код — MIT; внешние зависимости сохраняют свои лицензии.
